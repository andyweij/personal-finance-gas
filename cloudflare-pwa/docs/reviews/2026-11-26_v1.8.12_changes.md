### M3：參照完整性

- 範圍：同步寫入 `cashflow`、`recurring`、`asset`、`savings_adjustment`、`stock_tx` 時，本次有變更的 `ledgerId`、`linkedAccountId`、`accountId`、`assetId`，必須指向同一使用者、未刪除的紀錄。`default` 帳本永遠視為存在。
- 檢查寫在主寫入語句中（`AND EXISTS (SELECT 1 … deleted_at IS NULL)`），因此沒有 TOCTOU。寫入 0 列時再查一次參照，缺少的話回報 `RejectError`。
- 舊資料：只檢查「本次變更」的參照欄位（新建紀錄則全部檢查）。既有的懸空參照在只改備註等編輯時照常放行；改成另一個不存在的值則會被拒。
- 匯入：JSON 匯入的帳本參照必須能對應到 `default`、同份匯入中的帳本，或（merge 模式）雲端現有的帳本，否則整份匯入回 400。
- 匯入時刻意**不**拒絕懸空的帳戶參照：匯出檔本來就會包含帳戶已刪除的流水帳、存轉、持股交易，這些紀錄不影響任何餘額；若因此拒絕，這類備份將無法還原。新的懸空帳戶參照由同步寫入路徑擋下。

### M4：帳戶互轉的原子性

- `SyncMutation` 新增 `atomicGroupId`。轉帳的所有 mutation（兩邊與手續費）以及「同時刪除兩邊」都帶同一個群組 ID（等於 `transferGroupId`）。
- 伺服器：
  - 每個成員照常做驗證、版本檢查、M3 參照檢查，但不立即寫入。
  - 所有成員的語句放進同一個 D1 batch，每個成員的主寫入、冪等紀錄、change_seq 之後各加一條守衛語句。任何一筆 0 列變更，整個 batch 回滾。
  - 群組中任何一筆被拒或衝突，整組改為「拒絕」：客戶端回滾新建、完整重抓還原，內容保存在拒絕清單中。
  - 單獨修改既有轉帳某一邊的金額或帳戶會被拒絕；只改備註可以，兩邊在同一群組中一起修改也可以。
- 舊版客戶端（沒有 `atomicGroupId`）：同一個請求中 `transferGroupId` 相同的存轉新增會自動視為一組。單邊刪除仍允許（介面原本就提供「只刪這一邊」）。
- 客戶端：
  - 佇列以「單元」送出：群組不會被拆到不同請求，隔離模式下也是整組送出。
  - 整組多次失敗時一起隔離，後面的資料照常送出。

### M5：常態入帳的去重與舊資料相容

- 同名、同類型的兩個項目都會入帳。
- 排程與手動按鈕並行執行時，後寫入的一方略過，不會中斷、不會重複。一次性項目的停用語句加上 `changes() > 0`，不會重複停用。
- 相容既有資料：沿用舊名稱鍵入帳的列（或從備份還原、沒有鍵的自動入帳列），每一列視為「已入帳」並只抵銷**一個**符合的項目，優先抵銷金額與幣別相同的項目。因此先前因同名而漏入帳的另一個項目，在重新執行該月時會補上。

## 獨立審查與後續修正

以獨立的審查 agent 檢查第 2 組的 diff，要求以並行、離線、多分頁、新舊版混用、workerd 差異等情境找問題，並寫臨時測試重現。發現與處理如下：

| 嚴重度 | 問題 | 處理 |
|---|---|---|
| **阻擋** | R-D：前一筆轉帳被拒後，後一筆轉帳中「以前一筆為基礎」的那一邊被暫停（R6），另一邊卻單獨送出，伺服器出現半筆轉帳 | 新增 `collectHeldClosure`。暫停、回滾或隔離任何 mutation 時，佇列中同一群組的成員（遞移計算，包含這些成員所屬紀錄的後續編輯）一併以 `held_after_reject` 保存，並完整重抓。三條路徑都已套用：伺服器拒絕新建（R7）、拒絕編輯（R6）、隔離 |
| **阻擋** | R-A：離線新建帳戶、記一筆連動流水帳、再改帳戶名稱。合併後的帳戶 mutation 排到佇列最後，伺服器先處理流水帳時帳戶還不存在，M3 因此拒絕（相對舊版是退步） | 新增 `shared/syncOrder.ts` `orderMutationsByDependencies`：被參照紀錄（帳本或帳戶）的待送 upsert，連同該紀錄先前的 mutation，一律移到參照者之前，其餘順序不變。客戶端組批次前套用，伺服器處理每個請求前也套用，舊版客戶端因此也不受影響 |
| 中 | R-B：轉帳單元中間夾帶的無關 mutation 會和轉帳一起被隔離 | 隔離模式只送群組成員，以及成員所參照、位於同一段的紀錄 |
| 中 | R-C：離線新建的資產被合併進轉帳群組，轉帳被拒時連帶回滾該資產 | 不同群組（包括有群組和沒有群組）的 mutation 不再合併，兩筆依序送出，由 ack 後的 rebase 更新後一筆的版本。一併移除原本「兩個群組合併為一」的作法；對應測試已改為檢查「各自的群組、不跨群組合併」，原本的斷言因設計改變而更新 |
| 中 | #5：凍結項目重新套用時遺失 `atomicGroupId`，且逐筆略過，可能只套用一邊 | 保留 `atomicGroupId`。先判斷每筆是否略過，同一群組只要有一筆略過，就整組略過並列入清單 |
| 低 | R-F：群組內因 M3 被拒時，理由顯示為「已在其他裝置變更」 | 守衛失敗時，逐一對各成員重查參照，有缺少的就回報正確的理由 |
| 低 | `updateLocalPasskeysCache` 沒有序列化 | 加入 `serializedMethods` |
| 低 | 對帳校準的 USD 預設值仍以台幣反推 | 改用 `currentBalanceNative` |

審查確認沒有問題的部分：
- 群組 batch 的語句順序與 `changes()` 串接。
- 並行重送時直接 ack，不會重複寫入。
- epoch 改變時轉為 EpochMismatch。
- Proxy 綁定。
- M3 的 TOCTOU 防護與「只檢查變更」規則；已刪除帳本與已刪除流水帳的備份可以再匯入。
- M5 的部分唯一索引與 `ON CONFLICT` 語法、舊鍵相容。
- M7、M6、M8 的淨值與月底快照一致。
- M9 的跨分頁重載路徑。

## 行為變更

- 伺服器現在會**拒絕指向不存在或已刪除帳本 / 帳戶 / 持股的新寫入**。前提是參照有變更；舊資料的既有參照不受影響。
- JSON 匯入中有紀錄指向不存在的帳本時，整份匯入回 400，訊息會列出前 3 筆。
- **帳戶互轉的任何一邊失敗，整筆轉帳都不會寫入**，內容保存在同步失敗清單中。
- 單獨修改轉帳某一邊的金額或帳戶會被拒；目前介面沒有提供這項操作。
- 常態入帳：同名同類型的項目現在各自入帳。若某月過去因同名漏入帳，重新執行該月會補上漏掉的那一筆。
- USD 活存餘額改以美元加總，**顯示的台幣金額可能與先前略有不同**：先前是混用各筆流水帳記帳當時的匯率，現在一律用目前匯率換算。
- 手動入帳 API 收到不合理的年月時回 400。
- 同步的 400 / 413：只有在伺服器確認寫入健康時才會隔離資料。
- 同步佇列的送出順序可能調整：被參照的帳本 / 帳戶會先送出。

## 仍未處理

- 自動入帳（`automation.ts`）沿用常態項目上的 `linked_account_id`，帳戶事後被刪除時，產生的流水帳仍會連到已刪除的帳戶。這是既有行為，對餘額沒有影響。
- 股票交易與連動流水帳（買賣時同步記帳）仍是兩筆獨立的 mutation，沒有加入原子群組（不在本次範圍）。
- 群組 batch 中若有一筆因版本衝突失敗，伺服器回報的是整組「拒絕」而不是「衝突」：客戶端會還原雲端資料並保存內容，但不會出現「保留本機 / 保留雲端」的選擇。這是刻意的設計：讓單邊「保留本機」重送，會重新產生半筆轉帳。
