## Cloudflare 上限的確認結果

- 無法直接開啟官方文件：這個工作環境的網路政策擋下 `developers.cloudflare.com`。
- 以網路搜尋取得的官方頁面摘要：
  - [Workers Limits](https://developers.cloudflare.com/workers/platform/limits)：對外請求（subrequest）Free 為 50、Paid 為 10,000（可調到 1,000 萬）。
  - [D1 Limits](https://developers.cloudflare.com/d1/platform/limits)：每次 Worker 呼叫的 D1 查詢數 Free 為 50、Paid 為 1,000。
  - [2026-02-11 changelog](https://developers.cloudflare.com/changelog/2026-02-11-subrequests-limit)：Free 方案「50 個外部請求、1,000 個對 Cloudflare 服務的請求」。
- 兩份文件對 Free 方案 D1 查詢數的說法不一致，因此依交接說明採保守值設計：**每次呼叫 50 次 D1 查詢、50 個對外請求**。
- **假設（需部署後確認）**：一次 `db.batch()` 計為一次查詢。這是 D1 的計費與上限單位（一次往返）；若實際上 batch 內的每個語句各計一次，同步的預算需再調低。
- 付費方案可在 `[vars]` 設定 `D1_QUERY_BUDGET`、`SUBREQUEST_BUDGET` 放寬上限。

### H5：同步的 D1 查詢數

- 修正前與修正後的往返次數：

  | 階段 | 修正前 | 修正後 |
  |---|---|---|
  | 建立 / 讀取基本資料（設定、房租設定、預設帳本、同步狀態） | `ensure*` 4～6 次往返 | `ensureSyncBaseline` 一個 batch |
  | 冪等檢查與每筆資料的現有列 | 每筆各查 | 預先讀取，一個 batch |
  | 寫入 | 每筆一個 batch | 每筆一個 batch（不變） |
  | delta、游標與 epoch | 前後各讀一次 epoch，加 R-4 重試迴圈 | `readDeltaWithState` 一個 batch |
  | 以帳本刪除確認關聯紀錄 | 3 次查詢 | 1 次查詢 |

- 一致性：D1 的 batch 是單一交易，資料、游標與 epoch 一定一致，因此取代舊的前後 epoch 讀取與 R-4 重試迴圈。
- 每筆 mutation 內不再呼叫 `ensure*`。
- 預算守門：
  - 每個請求以 `countD1Queries` 計算已使用的查詢數。
  - 開始處理下一個單元前，先確認「已用＋每筆最壞 10 次＋回應 3 次」不超過預算（50 − 驗證保留 5）。
  - 每次請求最多處理 `SYNC_MAX_MUTATIONS_PER_REQUEST = 20` 筆；超出的 mutation 不回 ack，客戶端下次再送。
  - 第一個單元一定會處理，所以每次請求都有進度。
- 客戶端預設批次大小改為 20，與伺服器一致。
- 伺服器「超過 200 筆回 400」的硬上限保留，以相容一次送 50 筆的舊客戶端（舊客戶端照常運作，只是分 3～4 次完成）。

### H6：排程

- 執行順序：
  1. 補跑錯過的期間：上月月底快照、本月常態入帳。每月 1 號這一步就是正常入帳，因此**先入帳再更新報價**。
  2. 每日清理（僅每日排程）。
  3. 報價與匯率。
  4. 月底快照（在當日收盤價之後）。
- 每個步驟各自 try/catch 並 `console.error`。
- 執行紀錄：
  - 新表 `automation_runs` 記錄每位使用者每個期間的 `done` / `partial` / `failed`，已經是 `done` 的不會被降級。
  - 補跑只涵蓋當月之前就存在的帳號。
  - migration 只把「本月已有自動入帳」、「上月已有快照」的期間標為 done，部署本身不會回補過去的期間。
- 對外請求：
  - 所有對外請求經由 `createBudgetedFetch`：每次執行最多 50 個，且一律加上 `AbortSignal.timeout(8s)`。
  - 剩餘額度不足一次完整查價（8 個請求）時停止，剩下的留給下次。
  - 依 `quote_checked_at`（最久未嘗試者優先）輪替。
- D1 查詢也共用 50 次的預算。
- 手動更新報價（`/api/market/refresh`）套用相同的預算與逾時。

## 獨立審查與後續修正

| 嚴重度 | 問題 | 處理 |
|---|---|---|
| 中 | 「最久未更新優先」會永久餓死正常標的：查價失敗或報價不變時 `price_updated_at` 不會變，8 個下市代號就能每次耗光額度（已重現） | 0016 新增 `asset_items.quote_checked_at`。每次嘗試不論成敗都更新，所有標的在執行結束時以一個 batch 一起標記；排序改用此欄位 |
| 低～中 | 匯入時 `id`／`createdAt`／`priceUpdatedAt` 若是物件或陣列，會以 JSON 文字存入；`true` 會變成 `'1'` 而互相覆蓋（已重現，workerd 也一樣） | 預先驗證：這些欄位必須是文字或省略，否則回 400 |
| 低 | 部署當月的補跑可能補出 1 號時還不存在的常態項目；`partial`／`failed` 期間使用者刪掉的自動入帳會被救回 | 1 號之後的補跑只入帳「當月 1 號前就存在」的項目；排程執行時，本月已刪除的自動入帳也視為已入帳（手動重跑維持原本行為） |
| 低 | 補跑快照時，活存基準若已在快照日之後重設，會把之後的狀態算進快照 | 從基準金額扣回快照日到基準日之間的流水。手動資產與股價仍是補跑當下的值，見「仍未處理」 |
| 低 | 月底那次排程的報價步驟可能耗光 D1 額度，月底快照因此延到隔天 | 月底那次排程先計算「使用者數 × 5 ＋ 6」作為快照保留額度，補跑與報價都不會用到這部分 |
| 備註 | 伺服器硬上限 200 與客戶端 20 字面上不一致 | 實際由 `SYNC_MAX_MUTATIONS_PER_REQUEST = 20` 限制每次處理的筆數；200 是為了相容舊客戶端而保留的硬上限，已在上方與 `DATABASE_SCHEMA.md` 說明 |

審查確認沒有問題的部分：
- 「一個 batch 等於一筆交易」的論點成立：N2、Q2、P2-S2 與舊版 `since` 客戶端的行為與修正前等價。
- 預先讀取的資料列不會造成過期值：同一筆出現兩次會重新讀取；寫入其他列時會清除快取。
- 最壞路徑在預算內；部分 ack 時，新舊客戶端都會繼續送剩下的 mutation，不會累加隔離次數。
- `d1Budget` 只會高估查詢數（安全的方向）。
- 匯入的 9 張表，欄位與值逐一對齊。
- 15,000 個隨機浮點數經 `json_extract` 往返後完全一致。
- 1 號先入帳再更新報價。
- 0016 在 workerd 套用成功。

## 行為變更

- **同步一次最多處理 20 筆**。一次送更多筆的舊客戶端會分多次完成，不會被拒絕。
- **排程錯過的常態入帳與月底快照會自動補跑**：
  - 常態入帳：只補「當月之前就存在的帳號」、以及 1 號時就存在的項目。
  - 月底快照：日期為上月最後一天，只計入當天以前的紀錄。
- 每次執行最多 50 個對外請求，超出的標的留給下次（最久未嘗試者優先）。報價較多時，可能要等幾次排程才會全部更新。
- 匯入：
  - 超過 2 MB 回 413；格式錯誤回 400（以前可能是 500）。
  - 指向不存在帳本的紀錄回 400（v1.8.12）。
- CSV 匯入：
  - 重複匯入同一份檔案不會再新增重複資料。回應中的 `importedCount` 為實際新增的筆數，另有 `parsedCount`。
  - 列 ID 改為確定性 ID（`csv-…`）。
- 月底快照的日期依 `APP_TIMEZONE` 計算。
