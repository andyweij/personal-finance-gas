## 需修正（已寫成驗收測試）

### V1. 只有寫入路徑故障時，正常資料仍會被隔離（已確認）— `web/src/sync/syncEngine.ts:3051`
```ts
const isItemSpecificFailure = isDeterministicPayloadError || pullRes.ok;
```
以「純拉取成功」作為伺服器健康的證據。但如果故障只發生在寫入路徑（例如 D1 寫入錯誤或額度用盡），帶 mutation 的請求回 503、純拉取卻正常，**每一筆正常 mutation 都會被當成毒丸**。驗收測試中 5 筆正常資料全部被隔離；新建的紀錄還會從本機畫面移除。
- 修正：只有在「另一筆不同的 mutation 單獨送出成功」之後，才把先前失敗的那筆視為毒丸（例如先單獨試下一筆，它成功才隔離最前面那筆）；沒有這個證據時，5xx 一律不視為個別項目的問題。

### V2. 延後同一筆紀錄時，後面依賴它的 mutation 會插隊（新回歸，已確認）— `syncEngine.ts:2437`
```ts
if (seenKeys.has(key)) continue;
```
遇到同一筆的第二個 mutation 時用 `continue` 跳過，後面其他紀錄的 mutation 就排到它前面。重現：新帳本中的一筆紀錄送出失敗（已標記送出過）→ 刪除帳本並把紀錄搬到預設帳本 → 這一批變成「紀錄新建（已送出）、帳本刪除」，搬移紀錄的那筆被延後 → 伺服器以「此帳本仍有 1 筆關聯紀錄」拒絕刪除帳本。**使用者的刪除帳本操作變成錯誤。**
- 修正：遇到第一個重複的鍵就 `break`，讓每一批都是 outbox 的嚴格前綴；或一旦某個鍵被延後，其後所有 mutation 都一起延後。

### V3. 重新套用時被略過的凍結項目被靜默丟棄 — `syncEngine.ts:482-510`、`ui/conflictUi.ts:199`
被略過的項目直接隨 `frozen_outbox = []` 消失，不會成為拒絕或衝突紀錄；提示只寫「保留 N 筆凍結後較新的紀錄」，沒說是哪幾筆、也沒說還原前的編輯被丟掉了。伺服器端的更新（例如報價更新改了 `updatedAt`）也可能讓編輯在使用者不知情下被略過（待確認）。
- 修正：被略過的項目以拒絕紀錄保存（例如狀態 `skipped_newer`，保留 `clientPayload`），讓使用者能檢視或手動重新套用，並在 UI 列出。

### V4. 舊 epoch 的 mutation 依還原後的資料被「拒絕」（已確認）— `worker/sync.ts:2337-2341`（例：刪除帳本 `:799-801`）
請求途中發生 replace 後，舊 epoch 的刪除帳本依還原後的資料被拒絕（「帳本仍有 1 筆關聯紀錄」），同一個回應又標示 `epochMismatch: true`。客戶端因此丟掉一筆應該被凍結的 mutation，並顯示誤導的錯誤。驗證錯誤與確定性約束錯誤的 `RejectError` 也一樣。
- 修正：`RejectError` 分支與確定性約束分支中呼叫 `getCurrentDataEpoch`，與 `expectedEpoch` 不同時設定 `epochChangedDuringMutations` 並 `break`。

## 其他問題（未寫成測試）

- **R-1** `reapplyFrozenOutboxTx`（`web/src/db/localDb.ts:629, 673`）在 IndexedDB 的 success callback 內執行 `transform`，且沒有 `tx.onabort`。`transform` 一旦拋錯，交易中止但 promise 永遠不會結束；因為它在 `runSerialized` 內，**之後所有編輯與同步都會永久等待**（已用臨時測試確認會卡住）。觸發需要異常資料，機率低。→ `transform` 包 try/catch、`tx.abort()` 並 reject；加上 `tx.onabort`。較舊的交易方法也缺 `onabort`。
- **R-2** 沒有 `clientEpoch` 的客戶端（新裝置、或 meta 被重設）在任何 replace 之後，只要帶 mutation 就一律回 `epochMismatch` + 完整資料（`worker/sync.ts:2256-2258`），永遠無法 ack。可能是刻意的設計，但需寫入文件；建議至少確認 `clientEpoch: null` 的客戶端會採用回傳的 epoch。
- **R-3** `poisonSearchActive` 只在 outbox 清空、隔離、epoch 凍結時清除（`syncEngine.ts:3057`）。大批次偶發一次 500、單筆探測成功後，只要持續有新編輯就一直維持每批 1 筆。只影響速度 → 第一次單筆成功後清除。
- **R-4** 完整重抓的重試只做一次（`sync.ts:2232-2236`）；重試期間再發生第二次 replace，回應可能混合兩個 epoch。下次請求會自癒。
- **R-5**（本次 diff 之外，待確認）伺服器端自動入帳（`worker/automation.ts:73-159`）讀取常態項目與寫入是不同 batch，寫入未加 epoch 條件，中間發生 replace 時可能把舊 epoch 的自動入帳寫進還原資料。
- **R-6** v1.8.6 以前凍結的項目沒有比對基準欄位，會略過「較新編輯」檢查直接覆蓋；第二次還原時舊的凍結項目沿用第一次的基準（通常會被略過，屬保守結果）。
- **R-7** 另一個分頁已經重新套用時（凍結清單已空），提示仍顯示「已將待送變更重新套用」。
- **R-8** `recordIdempotencyOnly`（`sync.ts:570-583`）有一個理論上不會發生的分支會靜默 ack，改為拋錯較安全。
