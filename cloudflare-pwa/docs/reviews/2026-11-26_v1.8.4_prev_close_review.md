# 昨收修正審查（commit `6358b29`，v1.8.4）

- **對照規格**：[`2026-11-26_stock_prev_close_fix.md`](./2026-11-26_stock_prev_close_fix.md) 第 1～6 點
- **驗證**：`tests/stock-prev-close-fix.test.ts` 6 個測試通過；HEAD 全部 128 個測試通過。標「已確認」者已對照程式碼。TWSE MIS 的欄位行為（`v`、`ip`、試撮時段）無法連線實測，標「待確認」。路徑相對於 `cloudflare-pwa/`。

## 總評

原本造成漲跌異常的主因都已修好：MIS 盤中無成交不再把昨收當現價、06:00 排程只更新美股、`COALESCE` 沿用舊昨收已移除、Yahoo `chartPreviousClose` 已移除並改打 `range=1d`、報價來源不會混用。剩下的問題集中在 **客戶端 payload 省略報價欄位後的連帶影響**，以及 MIS 的試撮／零成交情境。

## 各項判定

| 項目 | 判定 | 說明 |
|---|---|---|
| 1. MIS `z='-'` | ⚠️ 部分 | 改為 z → 第一檔買賣中間價 → 單邊 → 開盤 → 交給 Yahoo（`worker/market.ts:451-481`），不再用 `y` 當現價。未處理開盤前試撮、收盤集合競價、整天零成交（F2、F3） |
| 2. 06:00 排程 | ✅ | 22:00 UTC 與每月 1 號 00:00 UTC 改為 `marketScope: 'us'`；23:00 台北時間仍更新全部；手動更新不受影響 |
| 3. `COALESCE` 沿用舊昨收 | ✅ | 改為 `previous_close = ?`；抓取失敗則價格與昨收都不動，維持一致 |
| 4. Yahoo `chartPreviousClose` | ✅ | 已移除；5d 拿不到昨收時改打 `range=1d` |
| 5. 持股視窗手動改價 | ⚠️ 部分 | 新增 `stPrevClose` 欄位與 `resolveStockModalPriceFields`；未改價時不送價格、改價未改昨收時清除昨收。但有 F1、F4、F5 |
| 6. 報價由伺服器擁有 | ✅ 大致完成 | `worker/sync.ts:1336-1349` 對既有「自動更新」資產保留伺服器報價，除非帶 `manualPriceOverride`。但報價更新仍遞增 version，仍會產生假衝突（F7） |

其他確認沒問題的部分：
- 委買委賣字串解析（`'1050.0000_1045.0000_'` 結尾底線、`'-'`、`'0.0000'`）正確。
- 漲停（`a='-'`）取委買、跌停（`b='-'`）取委賣，皆為停板價，正確。
- 不會混用來源：只有現價也來自 MIS 時才用 MIS 的 `y` 當昨收；fallback 到 Yahoo 時兩者都來自 Yahoo。

## 需修正（依嚴重度）

### F1. rebase 與「保留我的」後，本機資產沒有價格（已確認）— `web/src/sync/syncEngine.ts:969-976` 搭配 `:1736-1739`、`:1847-1855`、`:2181-2190`
為了不覆蓋伺服器報價，未改價時會從 mutation payload 刪掉 `unitPrice` / `previousClose`。但 rebase 與衝突「保留我的」會用這個 payload 呼叫 `applyRecordToSnapshot`，而 asset 分支是 **整筆取代**（`[...filtered, record]`），結果本機資產的 `unitPrice` 變成 undefined，畫面顯示 NaN 或錯誤數值，直到下次拉取；離線時會一直這樣。
- 情境：同步拉回排程更新的資產時，使用者剛好在改成本；或衝突時選「保留我的」。
- 修正：asset 套用 payload 時改為疊加在伺服器或既有紀錄上（`{ ...serverOrExisting, ...payload }`）。加測試：省略報價欄位的 upsert 經 rebase / 保留我的之後，本機價格仍存在。

### F4. 只改昨收時會送出本機舊價格並覆蓋伺服器（已確認）— `shared/validation.ts:370-374`
價格沒改、只改昨收時，回傳 `unitPrice: existing.unitPrice`（本機 snapshot 的舊價格）加上 `manualPriceOverride: true`，繞過伺服器保護，把較新的伺服器價格覆蓋回舊值。
- 修正：價格未改時只送 `previousClose`。需要一個「只覆寫昨收」的旗標，或從 payload 省略 `unitPrice`，伺服器只更新有帶的欄位。

### F2. 開盤前試撮價被當成現價（待確認）— `worker/market.ts:456-463`
08:30～09:00 MIS 的 `z='-'`，委買委賣是試撮價。此時手動更新會把推測性的中間價寫進 `unit_price`。
- 修正：查證 MIS 的試撮旗標（可能是 `ip`）或依時段判斷，試撮期間回傳 null 交給 Yahoo，或不更新該列。

### F3. 收盤集合競價與整天零成交使用委買委賣中間價（待確認）— `worker/market.ts:456-474`
整天沒有成交但有掛單的股票，23:00 會把中間價寫入而不是 `y`，產生假漲跌。規格允許「確定當日無成交」時用 `y`。
- 修正：查證成交量欄位 `v`，若為 0 或 `'-'`，現價用 `y` 並視為平盤。

### F5. 更換代號後沿用舊代號的價格 — `worker/sync.ts:1345-1348`、`shared/validation.ts:356`
價格沒改時不送 `unitPrice`，伺服器就把舊代號的 `unit_price` 留在新代號上，直到下次更新報價；客戶端本機也保留舊昨收（`syncEngine.ts:916-923`），而伺服器設為 NULL，兩邊不一致。
- 修正：代號改變時把價格設為 0 / null（顯示「待更新」）並觸發一次報價抓取。

## 次要問題

- **F6** 持股視窗的昨收欄位預先帶入舊值；使用者改價但沒動昨收時會被清除。標籤有說明，但行為仍讓人意外 → 改價時即時清空欄位或提示。
- **F7** 報價更新仍遞增 version：沒同步到最新報價的裝置做任何持股編輯都會衝突。既然報價欄位已由伺服器擁有，可自動解決「只差在報價欄位」的衝突，或報價更新不再遞增 version（拉取已改由 `change_seq` 驅動）。
- **F8**（既有）23:00 台北時間的排程落在美股盤中，約 7 小時內顯示的是美股盤中價格，直到 06:00 才更新為收盤價。
- **F9** 伺服器保護未檢查 `existing.deleted_at`，重新 upsert 已軟刪除的自動資產會保留過時價格（`worker/sync.ts:1338`）。
- **F10** 沒有清理已錯誤資料的 migration 或部署說明。移除 `COALESCE` 後，下次成功更新會自癒；但一直抓取失敗的列、以及先前 06:00 寫成「現價 = 昨收」的台股列，要等到下次 23:00 或手動更新才會修正 → 部署後手動執行一次 `/api/market/refresh`，並寫入部署說明。
- **F11** `range=1d` fallback 每檔多一次 Yahoo 請求，增加排程時間；且未檢查結果與 5d 價格是否屬於同一交易日。

## 測試缺口

- 委買委賣中 `'0.0000'` 的檔位、tse|otc 雙筆 entry 迴圈、試撮與集合競價快照、零成交日。
- 更換代號。
- 省略報價欄位的 payload 走 rebase 與「保留我的」（F1）。
- 持股視窗只改昨收（F4）。

## 建議修正順序

F1 → F4 → F5 → 查證後修 F2、F3 → F7 → 其餘。部署後手動觸發一次報價更新（F10）。
