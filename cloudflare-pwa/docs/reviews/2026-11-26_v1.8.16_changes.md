# v1.8.16 修正紀錄（B7：移除租戶欄位的 `DEFAULT 'owner'`）

- **對照**：[`2026-11-26_full_review_v1.8.10.md`](./2026-11-26_full_review_v1.8.10.md) B7。v1.8.15 只做了程式層的檢查，見 [`2026-11-26_v1.8.15_changes.md`](./2026-11-26_v1.8.15_changes.md)。
- **新的 migration**：`0017_drop_owner_default.sql`
- 路徑都相對於 `cloudflare-pwa/`。

## 為什麼要重建資料表

`0007` 加入多使用者時，12 張資料表的 `user_id` 被設為 `NOT NULL DEFAULT 'owner'`，`owner` 就是管理員的 id。只要有一條 INSERT 漏寫 `user_id`，該筆資料就會悄悄記到管理員名下：
- 成員看不到這筆資料。
- 管理員會看到別人的資料。

v1.8.15 的測試只能檢查 `worker/*.ts`，管不到以下三種 SQL：
- migration 裡的 SQL
- 在 D1 console 手動執行的 SQL
- 以動態表名組出的 SQL

SQLite 不能修改欄位的 DEFAULT，所以只能重建資料表。

## 做法

12 張表都以同樣的步驟處理，整個檔案在同一個交易內執行：
1. 建立新表。新表的定義與目前完全相同，只是 `user_id` 改為 `TEXT NOT NULL`，沒有預設值。
2. 依欄位名稱逐欄複製全部資料。
3. 刪除舊表，並把新表改回原本的名稱。
4. 重建原本的 32 個索引，名稱與定義都不變，包含常態入帳防重複的部分唯一索引。

其他說明：
- 新表的 CREATE 語句是從 `0016` 之後實際的 `sqlite_master` 產生的，所以後來用 ALTER 加入的欄位也都包含在內。
- 涉及的表：`asset_items`、`auth_passkeys`、`auth_sessions`、`cashflow_logs`、`ledgers`、`networth_history`、`recurring_items`、`rent_utility_records`、`savings_adjustments`、`sinking_fund_items`、`stock_transactions`、`sync_idempotency`。
- `app_settings` 與 `rent_utility_settings` 本來就沒有這個預設值，不需要重建。
- 資料庫沒有外鍵與觸發器，重建不會影響其他表。

### 失敗時會整筆退回

第一次彩排誤用了舊的本機資料庫。那個資料庫建立時，`0016` 還沒有 `quote_checked_at` 欄位，所以 `0017` 執行時出現 `no such column: quote_checked_at` 而失敗。

失敗後檢查：
- 資料完全沒有變。
- 12 張表仍保有原本的預設值。
- 沒有留下暫存表。

這證實了兩件事：
- 檔案中途失敗會整筆退回，不會留下半套結構。
- 實際的 schema 若與預期不同（例如曾在 console 手動改過），migration 會直接失敗，不會悄悄漏掉欄位。

## 行為變更

- 使用上沒有差異。
- 之後若有任何 SQL 漏填 `user_id`，寫入會直接失敗，而不是記到管理員名下。

## 部署

1. 先備份：`npm run db:backup:remote`
2. 套用 migration：`npm run db:migrate:remote`。如果正式環境還在 `0013`，這一步會依序套用 `0014`–`0017`。
3. 部署：`npm run deploy`

補充說明：
- 第 2、3 步的順序不影響正確性，因為新舊程式在新舊 schema 上都能運作。
- 套用時 wrangler 會提示「資料庫可能暫時無法服務」。重建只需要複製一次資料，以個人記帳的資料量來說應在數秒內完成。
- 若第 2 步失敗，資料庫維持原狀。請保留錯誤訊息，不要手動修改資料表。
