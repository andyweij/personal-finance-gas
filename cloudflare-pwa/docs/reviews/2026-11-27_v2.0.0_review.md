## 發現 1（高）：SL-4 同帳本參照守衛只檢查變更過的參照

位置：`worker/sync.ts:1709-1713`（`applyRowEntityMutation`），`collectChangedRefs`（約 `:730`）。

M3 的參照檢查只檢查「本次寫入改動的參照」。這原本是為了相容舊資料中的懸空參照。SL-4 直接套在這份清單上，只替**有變更**的資產參照加上 `requiredLedgerId`。因此有兩條路徑可以繞過：

1. **分享前就存在的跨帳本連動。**
   - 「家用」帳本的流水常從個人預設帳本的活存付款（`linkedAccountId = ast_priv`）。
   - 帳本分享後，編輯者 Bob 會收到這筆流水，看得到私人帳戶 ID。
   - Bob 只改金額、不改連動帳戶時，伺服器不會重新檢查參照，寫入被接受。
   - 實測：金額 10 → 99999，Alice 的**私人活存餘額跟著被改動**。刪除這筆也一樣會改到餘額。
2. **擁有者寫入未帶 `sharedLedgerId` hint。**
   - `resolveMutationTarget` 只對「加入的他人帳本」從 payload 推斷共同範圍；擁有者自己的共同帳本必須由用戶端帶 hint。
   - 舊版用戶端，或尚未得知帳本已共享的裝置寫入時，落在個人範圍，可把共同流水連到私人帳戶。
   - 實測：沒有 hint 時被接受；帶 hint 時被拒。

建議：

- 共同範圍內的寫入（不論擁有者或成員），對**所有**資產參照都檢查 `requiredLedgerId`，不只檢查變更過的；刪除時也檢查既有列的連動帳戶。
- `resolveMutationTarget` 在 `payload.ledgerId`（或既有列的 ledger）屬於 `ownedSharedLedgerIds` 時，自動套用共同範圍。
- 產生第一張邀請碼時，掃描該帳本的跨帳本連動並提示擁有者（或要求先解除）。

## 發現 2（高）：SL-8 成員匯出帶走他人共同帳本

位置：`web/src/ui/securityUi.ts:1091-1112`。

「匯出完整 JSON」直接序列化 `engine.getSnapshot()`，CSV 匯出直接用 `getSnapshot().cashflowLogs`。實測 Bob 的匯出檔包含 Alice 的 `led_home`、帳戶與流水。若 Bob 再把這份 JSON 匯入，他人資料就會寫進 Bob 自己的帳號。

伺服器端的 `exportFullSnapshot` 只讀自己的 `user_id`，所以沒問題。問題出在 UI 用本機快照匯出。

建議：匯出前排除 `isShared && myRole !== 'owner'` 的帳本，以及其流水、帳戶、存轉、固定收支、拆帳、分期。

## 發現 3（高）：擁有者取代匯入後，成員的舊異動沒有凍結

位置：`web/src/sync/syncEngine.ts:4904-4906`、`:5103-5108`。

1. Bob 離線時在共同帳本新增一筆，Alice 在這段期間做 `replace` 匯入，然後 Bob 上線。
2. 伺服器正確地把該筆留為未確認，並標示 `epochMismatch`。
3. 用戶端只清除該帳本的快取再全量合併，**沒有把該帳本的待送異動移到 frozenOutbox**。
4. 下一次同步帶著新 epoch，把這筆舊異動寫進 Alice 還原後的資料。實測 `B-stale` 出現在伺服器上。

這違反 SDD §5.2／§8 的「單一共同帳本局部凍結」。

建議：處理 `epochMismatch` 的帳本時，把 `sharedLedgerId` 屬於它的待送異動移到 frozenOutbox，其他帳本照常同步。

## 發現 4（中）：取代匯入讓共同帳本變成孤兒

位置：伺服器 `worker/sync.ts`（`importFullSnapshot`），約 `:4057` 的 `DELETE … WHERE user_id = ?`；用戶端 `syncEngine.ts:4894-4914`、`:4048-4056`。

當 Alice 以分享前的備份做取代匯入時：

- **伺服器端：**
  - `led_home` 與其中所有紀錄（包括 Bob 新增的）都被硬刪除。
  - `ledger_members` 兩筆資格仍然有效。
  - `readSharedLedgersDelta` 因為找不到帳本而略過它，也沒有放進 `revokedSharedLedgerIds`（實測回應兩者皆空）。
  - Alice 的 `ownedSharedLedgerIds` 仍包含這個不存在的帳本，Bob 的加入上限也仍被佔用。
- **用戶端：**
  - 只拿掉 `isShared` 等標記，帳本與 Alice 的流水留在 Bob 的 IndexedDB，看起來像 Bob 的個人帳本。
  - cursor 也被移除，之後不會再被清除。
- **UI：** SDD SL-8 要求「擁有者 replace 還原時……明確提示共同帳本成員將重抓」，目前匯入對話框沒有任何提示。

建議：

- 取代匯入後，對備份中已不存在的帳本撤銷其成員資格（或保留這些帳本不刪除）。
- 匯入前若有共同帳本，顯示警告。
- 用戶端把「上次 `meta.sharedLedgers` 中非 owner、這次回應卻沒有出現」的帳本視同撤銷並清除。

## 發現 5（中）：邀請碼猜測限速可被重設

位置：`worker/index.ts:724-745`（第 738-739 行在核銷成功時清除 IP 與帳號計數器）。

攻擊步驟：攻擊者自己建立帳本並產生邀請碼，然後用第二個帳號循環「猜 4 次 → 核銷自己的碼（計數器歸零）→ 退出帳本」。實測同一 IP 猜了 16 次都沒被擋，正常情況下第 6 次就會回 429。

邀請碼為 32 字元集 × 12 碼，熵是 60 位元，所以實際猜中機率仍極低。但限速形同失效。

另外兩點：

- SDD 寫「128-bit 熵」與實作不符。
- 沒有 `cf-connecting-ip` 時會退回使用 `x-forwarded-for`，可被輪換來繞過。這是既有行為，只影響非 Cloudflare 部署。

建議：

- 核銷成功時只清除帳號計數器，不清 IP 計數器。
- 另加一個以 IP 為鍵、只累加的每日上限。
- 修正 SDD 的熵數字。

## 發現 6（中）：SL-7 撤銷清除不完整

位置：`syncEngine.ts:5103-5129`。

撤銷時已清除快照中的 7 類實體，也已用 `rolled_back` 移出待送異動，這部分實測正確。但 `nextConflicts` 沒有依撤銷的帳本過濾：實測撤銷後 IndexedDB 的 `conflicts` 仍有 `serverRecord.itemName = 'A-secret-acct'`。`frozen_outbox` 中屬於該帳本的項目也沒有清除（這點依程式碼推論）。

建議：在同一筆交易內一併過濾 conflicts 與 frozenOutbox。

## 發現 7（中）：viewer 共同帳本讓批次操作整批失敗

位置：`syncEngine.ts:4066-4075`、`:2783`（`postDueInstallmentsForMonth`）。

`commitAndMaybeSync` 只要遇到 viewer 帳本的異動就整批丟錯。實測 Bob 按「入帳分期」時，連他自己的個人分期也無法入帳。`reorderAssets` 遇到混合清單時也會一樣（依程式碼推論）。

建議：批次操作預先略過唯讀帳本的紀錄。

## 低嚴重度（8～13）

- **8.** 成員清單回傳其他成員的 `username` 與 `userId`（`sharedLedgers.ts:90,129-136`），方便針對成員帳號猜密碼。建議只回顯示名稱，或只讓擁有者看到 username。
- **9.** 成員上限與加入上限是先計數、再寫入，兩者分屬不同 batch，INSERT 沒有帶條件（`sharedLedgers.ts:365-440`）。建議把計數寫進 `INSERT … WHERE (SELECT COUNT…) < N`。
- **10.**
  - `ledger_members` 的主鍵 `(ledger_id, member_user_id)` 等於全域唯一。知道對方帳本 ID 的人可以先用同 ID 建帳本並發邀請，讓對方無法分享。預設 ID 是 UUID，所以風險低。
  - `DELETE /members/:id` 依成員資格是否存在回傳不同錯誤（`:516-524`）；「識別碼已被其他使用者使用」也會洩漏同 ID 帳本存在。
- **11.**
  - 帳本軟刪除時沒有作廢邀請碼；還原後舊碼恢復有效，軟刪除期間偏好更新也仍會成功。
  - join 等新路由直接用 `c.req.json()`，建議改用既有的 `readJsonBodyLimited`（約 4 KB）。
- **12.** `tryReadOnlyPull`（`syncEngine.ts:4604-4680`）沒送 `sharedCursors`，也不處理 `sharedLedgers` 與撤銷。這段期間會多傳全量資料，也可能短暫顯示已刪除的紀錄；之後的正常同步大致能補回。
- **13.** viewer 唯讀只在記帳分頁停用送出、隱藏刪除（`logTab.ts:556,907-922`）。資產、固定收支、信用卡、拆帳、存轉、快速範本的按鈕仍可按，按了由 engine 丟錯顯示 toast，本機不會被改。這與 SDD §8 的「自動隱藏」不符。

## 確認沒問題（已實測）

- **權限與 IDOR：** 下列操作全部被擋。
  - 非擁有者產生或作廢邀請碼。
  - editor 改他人角色、移除他人。
  - viewer 自行升級。
  - 把成員升為 owner，或擁有者把自己降級或移除。
  - 對 `default` 帳本、他人帳本或不存在的帳本操作。
  - 非成員更新偏好。
- **邀請碼：**
  - 字元集 32 能整除 256，沒有取模偏差。
  - 資料庫只存 SHA-256 雜湊。
  - 一次性靠原子 UPDATE 加 `changes()` 守衛；兩人併發核銷同一碼只成功一人。
  - 過期、作廢、已使用的碼都被拒，而且錯誤訊息一致，不洩漏碼是否存在。
  - 角色取自邀請碼本身，join 請求本文中的 `role` 會被忽略。
  - 被移除的成員可以用新碼重新加入。
- **路由防護：** 7 條新路由都有 `requireAuth`、CSRF 防護與 `X-Expected-User` 檢查。
- **SL-9：** 未套用 0025 時，GET 回空陣列，其他路由回 400 並附遷移提示。
- **同步寫入：**
  - SL-2：成員資格與角色的 `EXISTS` 檢查寫在同一條寫入 SQL 中，撤銷當下沒有 TOCTOU 空窗。
  - SL-1／SL-5：編輯者用擁有者私人紀錄的 ID 覆寫會被拒；跨個人與共同帳本、或跨不同共同帳本搬移紀錄會被拒。
  - 原子群組不可跨範圍。
  - viewer 無法寫入；只有擁有者可修改帳本設定。
  - 預設帳本不接受共同帳本操作。
  - 共同範圍寫入一律走嚴格參照檢查，不走 v1.8.11 的寬鬆模式。
  - 冪等鍵以 actor 為準。
- **用戶端：**
  - 一般撤銷與離線期間被撤銷時，7 類實體都會清除。
  - editor 降為 viewer 後，待送異動被拒並正確回滾。
  - 每帳本 cursor 正確維護。
  - 淨值計算採用成員自己的 `includeInNetWorth` 偏好。
  - 帳本選單排除 viewer 帳本；連動帳戶只列同帳本的帳戶。
  - SL-10：所有使用者輸入都用 textContent 或 escapeHtml 呈現。
  - `joinLedger` 網址參數用完即清除；sw.js 不快取帶參數的網址。

## 建議修正優先序

1. 發現 1（伺服器 SL-4 守衛）與發現 2（匯出過濾）：直接關係到他人資料的完整性與外洩，建議在更多使用者啟用共同帳本前修正。
2. 發現 3、4、6：取代匯入與撤銷的資料一致性。
3. 發現 5、7，其後是低嚴重度項目。
