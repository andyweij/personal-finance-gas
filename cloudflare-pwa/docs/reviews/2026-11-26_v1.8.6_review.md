## 需修正（依嚴重度）

### Q1. 伺服器短暫故障會把正常資料移出 outbox（新回歸，已確認）— `web/src/sync/syncEngine.ts:2923-2996`、`web/src/db/localDb.ts:305-335`
任何 5xx（含伺服器整體故障）都會讓這一批所有 mutation 的 `retryCount + 1`。第一次失敗後批次縮為 1 筆，之後每次暫時性 5xx 再 +1；預設 `maxPoisonRetries = 5`、退避 2/4/8/16 秒，**約 30 秒的故障就會隔離最前面那筆**。隔離後 `consecutiveFailures` 歸零並立即 `continue`（沒有延遲），下一批 50 筆又失敗、全部 +1，於是剩下的項目被隔離得更快。
- 結果：1～2 分鐘的故障可能把整個 outbox 移進拒絕清單。被隔離的新建會從畫面移除；被隔離的編輯會設 `pendingFullResync`，下一次完整重抓就把它們還原掉。資料只剩卡片裡的 JSON。
- 修正：
  - 只計算「批次為 1 筆時」的失敗次數。
  - 5xx 之後若有其他 mutation 成功（代表伺服器正常），才把先前的失敗視為該筆的問題；整體連續 5xx 不累計。
  - 優先只對 400 / 413、或「伺服器剛回應正常後」的 5xx 隔離。
  - 隔離後保留退避，不要立即重試。
- 測試：無論內容都回 500 的伺服器，持續 2 分鐘後恢復 → outbox 不得有任何項目被隔離。

### Q2. N2：完整重抓期間的寫入會漏掉（第二次確認、重現測試仍失敗）— `worker/sync.ts:2063-2064, 2178-2179, 2196-2197`
先 `querySyncDelta(null)`、後讀 `changeSeq`，兩者之間 commit 的寫入既不在 snapshot、也不在下次 delta。
- 修正：完整查詢之前先讀 `changeSeq`，以 `<= maxSeq` 限制查詢，回傳該值作為游標。

### Q3. R6：被拒的值仍會被送出並顯示為「已還原」— `syncEngine.ts:2720-2749, 2829, 2884`
E1 被拒時 E2（同一筆）已在佇列中：E2 先送出，帶著 E1 被拒的欄位，可能寫入伺服器；完整重抓時又把 E2 整筆 payload 疊上去，卡片寫「已還原」，畫面仍是被拒的值。
- 修正：被拒時把同一筆的待送編輯 rebase 到伺服器紀錄上，只保留該編輯自己改過的欄位；或暫停並請使用者確認，期間狀態維持 `pending_resync`。

### Q4. N1：自己的連續編輯產生假衝突；並與 R7 交互造成誤刪（未修）— `syncEngine.ts:2473, 2691-2718, 2751-2753`
- N1 本身：已送出的列與後續編輯同批送出，第二筆衝突。失敗後縮為 1 筆的批次只是暫時掩蓋，重新載入或 401 後（不會累加 `consecutiveFailures`）又會同批送出。
- 與 R7 交互（待重現）：新建 M1 已送出、後續 M2 標 `isNewRecord: true`，兩者同批 → 伺服器拒絕 M1、以 M2 建立並 ack；但相依過濾排除了同批項目，M1 的回滾仍在本機刪除該紀錄，而游標已前進 → 紀錄只存在伺服器上，卡片寫「已回滾」。
- 修正：每批每個 `entity:recordId` 最多一筆；同批若有同一筆已被 ack，就跳過回滾。

### Q5. N4：舊 epoch 的 mutation 寫入還原後的資料（第二次確認、重現測試仍失敗）— `worker/sync.ts:2082-2167`
- 修正：每筆主要寫入（或 idempotency 語句）加上 `AND (SELECT data_epoch FROM user_sync_state WHERE user_id = ?) = ?`；或每筆 mutation 前重讀 epoch。

### Q6. F8：月底淨值快照使用美股盤中價（未修）— `worker/index.ts:825-829`
23:00 台北時間的排程以 `'all'` 更新，落在美股盤中；月底時 `runMonthEndSnapshotAllUsersD1` 也在這次執行，**淨值歷史會記錄美股盤中價**。
- 修正：23:00 改為 `marketScope: 'tw'`（06:00 已負責美股），或把月底快照移到 06:00 美股收盤更新之後。

### Q7. F7：報價更新仍遞增 version，離線編輯持股必衝突（未修）— `worker/market.ts:710-716`
報價欄位已由伺服器擁有，但每次報價更新仍 `version + 1`；離線裝置在排程後編輯成本或備註都會衝突。
- 修正：報價更新不再遞增 version（拉取已由 `change_seq` 驅動）；或 asset 的版本檢查在差異只有報價欄位時自動接受。

### Q8. 更換代號、清空代號時價格歸零且不會自動補上 — `shared/validation.ts:364-370`、`stocksTab.ts:1521, 1946`、`worker/sync.ts:1292-1297`
`tickerChanged` 分支不看 `updateMode`：清空代號（變成手動或仍為自動但沒有代號）也會把價格設為 0，持倉市值變 0 且沒有提示。有效的新代號也要等到 23:00 或手動更新才有價格，可能被月底快照記錄為 0。另外，新建或復活已軟刪除的自動資產、未帶 `unitPrice` 時寫入 1，與更換代號的 0 不一致。
- 修正：只有「新代號非空且為自動更新」時才歸零；儲存後觸發單一代號報價更新，或顯示「待更新」；新建 / 復活的預設值統一為 0 + 待更新。

## 次要問題

- **毒丸在 outbox 中間時很慢**：每輪只有一筆正常 mutation 通過（50 筆失敗 → 1 筆成功 → 計數歸零 → 回到 50 筆），每輪都重複純拉取請求。不會無限迴圈 → 在找出壞的那筆之前維持 1 筆（或二分法）。
- **F1 邊界**：本機沒有該資產（另一台裝置刪除、或 replace 還原時被移除）時，只用 payload 建立紀錄，`unitPrice` 仍為 undefined；「重新套用」以 `isNewRecord: true` 送出且沒有價格，伺服器預設為 1 → 缺報價欄位時以 0 / 待更新補上，或不疊加。
- **F6 邊界**：在價格欄位輸入後又改回原值，昨收已被清空；送出時價格視為未改、昨收視為改成 null，帶著 `manualPriceOverride` 清掉伺服器的昨收 → 價格回到初始值時恢復昨收，或送出時與欄位初始值比對。
- **F2 / F3（待確認）**：13:25～13:30 收盤試撮期間 `t >= 09:00`、`ip` 未必是 4 / 5；收盤後 `z='-'` 但 `v>0` 仍用中間價；未檢查 `d`（日期）→ `t >= 13:30` 且 z 無效時優先用 Yahoo；以實際 MIS 資料確認 `ip` 代碼。
- **R5** 其餘路由仍以 400 回傳原始錯誤：`worker/index.ts:173, 211, 240, 292, 352, 372, 425, 445, 469, 483, 591, 788`。
- **R2 細節**：錯誤分類的 regex 不含 `UNIQUE`（真實 D1 訊息結尾為 `: SQLITE_CONSTRAINT` 時行為與 mock 不同，影響小）；拒絕訊息為通用文字、失去欄位名稱；`clientTimestamp` 未檢查型別；`mutationId` 非字串時以 `'unknown'` 拒絕，客戶端無法對應，該筆無法離開 outbox。
- **N3** 重新套用凍結項目仍會覆蓋較新編輯，且以記憶體清單寫回 `frozen_outbox=[]`。
- **狀態膠囊**：任何拒絕（含新的「已隔離」）都讓膠囊固定為衝突，隱藏離線與待送數量；搭配 Q1，伺服器故障會變成紅色衝突。
- **`tryReadOnlyPull`**：完整重抓那一輪的請求失敗時，純拉取會抓完整資料卻以增量方式合併，伺服器端的刪除不會反映（待確認）；也不會清除 `pendingFullResync`（無害）。
- **`utility_record`**：驗證會截斷 period 至 20 字，但存在檢查用未截斷的 `normalizedPeriod`，INSERT / UPDATE 用截斷後的 `v.period`，超過 20 字的 recordId 會誤判衝突；`sync_lww_timestamps` 仍用未 trim 的 `recordId` → 超過 20 字直接拒絕。
- **F10 部署說明誇大**：`DATABASE_SCHEMA.md` §6 說下次排程會修正所有自動更新項目，但一直抓取失敗的列永遠不會被重寫 → 修正說明，或提供一次性 SQL 標記 `price_updated_at` 早於部署日的列。
- 未做：`auth_challenges(expires_at)` 索引、`locked_until` 清理、刪除帳本衝突 vs 拒絕、F11。
