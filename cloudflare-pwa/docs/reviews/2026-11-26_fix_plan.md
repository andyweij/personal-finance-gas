# 任務：修正 cloudflare-pwa 的設計缺陷

你是這個專案的原作者。本次範圍**僅限 `cloudflare-pwa/`**，請勿修改根目錄的 GAS 版（`src/`、`web/`、`tests/logic.test.mjs`、`appsscript.json` 等）。以下是一份外部設計審查的結果，請依**優先順序分階段**修正。行號以 commit `9e03fa5`（cloudflare-pwa v1.7.1）為準，若已有變動請自行定位。下文路徑皆相對於 `cloudflare-pwa/`。

## 工作規則

1. **分階段提交**：每個階段一個（或數個小）commit，沿用既有的 commit 格式（`fix(cloudflare-pwa): vX.Y.Z ...`），並更新 `package.json` 版本與 `web/src/version.ts`。
2. **每個修正都要有測試**：先寫一個能重現問題的失敗測試，再修正。使用 vitest（`cloudflare-pwa/tests/`）。
3. **不得破壞既有資料**：Schema 變更一律新增 migration（目前已用到 `0012`，新的從 `0013_...sql` 起），不要修改舊 migration；需考慮已部署 D1 中的舊資料與舊版客戶端（沒有 `baseVersion` 的 legacy client）。
4. 每階段結束執行 `npm run typecheck && npm test`（於 `cloudflare-pwa/`），全部通過才進下一階段。
5. 若某項你判斷審查有誤或不值得修，請說明理由後跳過，不要硬改。
6. 文件（`cloudflare-pwa/docs/SDD*.md`、`cloudflare-pwa/README.md`）與程式行為不一致處，修正時一併更新。

## 第一階段：立即修正（小改動、高風險）

### 1.1 Passkey 登入 challenge 未綁定 — `worker/auth.ts:770-777, 885, 895`
`consumeChallenge('authenticate', null)` 取全站最新 challenge 並先刪除，造成併發登入失敗，且可被無限呼叫 options 端點而癱瘓所有人的 Passkey 登入。
- 從 `response.response.clientDataJSON` 解出 challenge，以 `DELETE FROM auth_challenges WHERE challenge=? AND purpose='authenticate' AND expires_at>? RETURNING challenge` 原子性取用。
- 對 `/api/auth/passkey/login/options` 加速率限制。

### 1.2 Passkey 註冊可覆蓋他人 — `worker/auth.ts:840-846, 858-870`
`INSERT OR REPLACE` 以 `credential_id` 為鍵；login options 帶 username 時會把該用戶的 credential ID 回給未登入者。
- 改為一般 `INSERT`，ID 已存在則拒絕。
- login options 不再依 username 回傳 `allowCredentials`（改走 discoverable login）。

### 1.3 樂觀鎖競爭條件 — `worker/sync.ts:385-442` 及所有寫入
目前在 JS 比對版本後無條件寫入。
- 所有 UPDATE / 軟刪除改為 `WHERE user_id=? AND id=? AND version=?`，檢查 `meta.changes === 1`，否則回報 conflict。
- 新建改 `INSERT ... ON CONFLICT DO NOTHING` 並檢查 changes。
- 加測試：兩個相同 `baseVersion` 的 mutation 併發送出，只能有一個成功。

### 1.4 寫入非原子性 — `worker/sync.ts:1373-1378, 1433-1445`、`worker/automation.ts:112-150`
- mutation 與 `sync_idempotency` 寫入合併到同一個 `db.batch([...])`。
- replace 匯入：先完整驗證所有資料，再把 DELETE + INSERT 放入同一 batch（必要時分塊，但需確保失敗不留下半套資料）。

### 1.5 客戶端忽略 `rejected` — `web/src/sync/syncEngine.ts:1497-1500`
`SyncResponse.rejected` 從未被讀取，被拒的 mutation 永遠留在 outbox。
- 被拒 mutation 移出 outbox，放入「同步失敗」清單並在 UI 顯示（可參考 conflictUi），本機紀錄回滾或標記。

### 1.6 未知 entity/op 被靜默確認 — `worker/sync.ts:444-1274, 1357-1379`
- 白名單 entity 與 op，未知者放入 `rejected`，不得 ack。

## 第二階段：同步正確性

### 2.1 同步進行中編輯會與自己衝突 — `web/src/db/localDb.ts:248-267`
outbox 合併時不區分「已送出等待回應」的 mutation。
- 記錄 in-flight 的 mutationId，不合併進它們；新的 mutation 在 ack 後以新 version 作為 baseVersion（比照 settings 在 `syncEngine.ts:1505-1530` 的 rebase 作法）。
- 「新建後刪除互相抵銷」只在新建尚未送出時成立，否則排一筆 delete。
- 測試：(a) 同步中再次編輯同一筆；(b) 同步中刪除剛新增的紀錄 — 兩者都不得產生衝突或死而復生。

### 2.2 增量同步游標可能漏資料 — `worker/sync.ts:1349, 391-393, 1290-1298`
以請求開始的 `serverTime` 作游標、查 `updated_at > since`，交錯請求會漏掉變更；legacy client 用 clientTimestamp 寫 `updated_at` 會造成時鐘偏差。
- 新增伺服器遞增的 `change_seq`（每次寫入於同一 batch 中遞增），以此為游標；保持對舊游標的相容。
- `updated_at` 一律使用伺服器時間。

### 2.3 Replace 匯入破壞其他裝置 — `worker/sync.ts:1434-1441, 1456, 1502`
硬刪除且 version 重設為 1。
- 改軟刪除並遞增 version，或新增 per-user `data_epoch`，客戶端發現 epoch 改變時強制完整重抓。

### 2.4 伺服器更新資料未遞增 version — `worker/market.ts:508-521, 562-569`
- 報價與匯率更新需 `version = version + 1`；更好的做法是報價存獨立欄位/資料表，不被客戶端 upsert 覆蓋。
- Cron 不應覆蓋使用者手動設定的 `usd_twd_rate`（改為使用者可選擇的自動模式）。

### 2.5 跨帳號寫入 — `web/src/sync/syncEngine.ts:1451-1459`
- 同步請求帶 `X-Expected-User`（本機資料庫的 user id），伺服器不符回 409，客戶端停止同步並提示。
- 使用 BroadcastChannel 通知其他分頁帳號已切換。

### 2.6 重試、逾時、批次
- fetch 加 `AbortController`（約 20 秒逾時），避免 `syncingPromise` 永久懸置。
- 5xx / 網路錯誤採指數退避 + jitter；outbox 非空時定期重試。
- 客戶端每次最多送 ~50 筆 mutation 分批推進；伺服器端設上限與 body 大小限制。
- 用 `navigator.locks.request('sync', ...)` 避免多分頁同時送出同一份 outbox。

### 2.7 狀態先改後存 — `syncEngine.ts:271-286` 等 CRUD 方法
- 先算出新 snapshot → commit 到 IndexedDB → 成功才指派並 emit；失敗則還原並 toast。

## 第三階段：認證與本機資料保護

1. **登出清除本機資料** — `web/src/ui/securityUi.ts:1109-1116`、`main.ts:354`：登出時刪除該使用者的 IndexedDB 與記住的帳號；伺服器回報未登入時，即使有本機資料也要先通過 PIN/Passkey/密碼才顯示。
2. **不再下發 PIN 雜湊** — `worker/index.ts:122-124`、`worker/auth.ts:386`：PIN 驗證移至伺服器並限速；離線解鎖改用每裝置的獨立 verifier。UI 端加嘗試次數與指數延遲（`securityUi.ts:504, 525`）。
3. **離線 WebAuthn fail-open** — `web/src/auth/offlineWebAuthn.ts:225, 235`：非 ES256 或公鑰為空時必須拒絕。
4. **鎖定畫面**：鎖定時 `#app` 設 `inert`；`visibilitychange: hidden` 時自動上鎖（避免 iOS 多工畫面露出金額）。在 UI 與文件中明確說明這是「隱私遮罩」而非加密；若要真正保護，請提出以 AES-GCM 加密 snapshot（金鑰由 PBKDF2/Argon2 或 WebAuthn PRF 衍生）的方案，**先寫 SDD 再實作**。
5. **登入速率限制** — `worker/auth.ts:236-281`：改為驗證前原子 `INSERT ... ON CONFLICT DO UPDATE SET fail_count=fail_count+1 RETURNING`；新增 per-username 計數；`/api/auth/setup` 也要限速。未知使用者也要跑一次 PBKDF2 避免時序洩漏帳號存在。
6. **Session**：加絕對上限（如 `created_at` 起 90 天）；`last_seen_at` 超過一天才延長；Cron 每日清理過期的 sessions / challenges / rate_limits / sync_idempotency。
7. **管理員重設密碼**：寫入稽核紀錄、成員下次登入時提示「密碼已被管理員重設」、撤銷其 Passkey 與 PIN；並修正 `docs/SDD_multi_tenant.md` 對信任模型的描述。
8. **`user_id DEFAULT 'owner'`**（migration 0007、0011）：新 migration 重建表格移除預設值，並加 `REFERENCES users(id) ON DELETE CASCADE`。
9. **參照完整性** — `worker/sync.ts:635-638, 1052, 1117, 518-539`：`ledgerId`、`linkedAccountId`、`assetId`、`accountId` 必須確認屬於同一使用者且未刪除。
10. **安全標頭**：加入 CSP（`script-src 'self'`）；`shared/csv.ts:13-19` 的 `escapeCsvCell` 對 `= + - @` 開頭的儲存格加 `'` 前綴。
